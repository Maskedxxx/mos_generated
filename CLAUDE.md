# mos_generated — ИИ-генерация документов

Сервис создаёт готовые `.docx` по утверждённым шаблонам заказчика: подставляет реквизиты
организации, должности, ФИО, даты, номера. Дуален сервису проверки — тот ПРОВЕРЯЕТ
те же типы документов, этот их СОЗДАЁТ.

## ⚠️ Первое, что нужно знать

**У репозитория нет удалённого репозитория.** Единственная копия кода, шаблонов и данных
живёт на стенде `ms-llm-dev`. Резервных копий нет. Соответственно — не удалять каталоги
не глядя и не делать разрушительных операций без бэкапа.

   `screen -S mosgen -X quit; screen -dmS mosgen bash -c "cd ~/projects/mos_generated && .venv/bin/uvicorn api:app --host 0.0.0.0 --port 8090 >/tmp/mosgen.log 2>&1"`
2. **Не коммитить и не пушить без слова владельца.** Идентичность коммитов:
   `Maskedxxx <aangers07@gmail.com>`, без постфикса Claude.
3. **Шаблоны `templates/*.docx` — рабочие файлы заказчика.** Перед правкой делать бэкап
   (`/tmp/tpl_<тип>.bak.docx`), править точечно через zip + regex по `word/document.xml`.
4. **Журнал генерации не должен ронять выдачу документа.** Вся запись трейса — под `try/except`:
   человек должен получить файл, даже если журнал недоступен.

## Как устроено

**Точка входа одна — `engine.generate(doc_type, session_id, values, client)`**. Через неё проходят
оба HTTP-пути, поэтому логика наследования, стора значений и журналирования пишется только там:

| Эндпоинт | Назначение |
|---|---|
| `POST /api/types/{t}/generate` | генерация по JSON |
| `GET /api/types/{t}/download` | нативное скачивание (браузер сохраняет сам по `Content-Disposition`) |
| `GET /api/graph` | список типов с кодами — фронт рисует выпадающий список |
| `GET /api/types/{t}/schema` | схема полей: `{key, label, required, source, hint}` |
| `GET /api/orgs`, `GET /api/org/suggest?org=` | автозаполнение по организации |

**15 типов**, все — Word через `docxtpl`. Генератор типа лежит в `generators/<тип>.py`
и содержит `SCHEMA` (поля формы) и `context()` (подготовка значений под шаблон).
Реестр — `registry.py`, граф с кодами — `graph.json`.

**Автозаполнение по организации.** Стор `_org_store.json`: ключ — нормализованное название
(`engine.normalize_org` снимает юрформу, кавычки, пунктуацию, регистр), значение —
`поле → список ранее введённых значений`. Пополняется в конце каждой генерации.
Перенос между типами работает по совпадающим ключам полей: чего раньше не вводили,
в новом типе останется пустым.

**Журнал генерации.** На каждый вызов пишется `logs_generated/<тип>/session_<время>/`:
`meta.json` (время, тип, IP, статус, размер), `values.json` (чем заполняли), копия `.docx`.
Отказы тоже журналируются со `status: "error"`. Счёт выпущенного:
`find logs_generated -maxdepth 2 -type d -name "session_*" | wc -l`.

## Стек

Python 3.12, FastAPI + uvicorn, `docxtpl` + `python-docx`, `openpyxl`.
Языковая модель НЕ используется — генерация детерминированная, подстановка в шаблон.
Фронт: собственный `static/index.html` (legacy, отдаётся самим FastAPI) и React-экран
в составе объединённого интерфейса проверки.

## Дерево проекта

```
api.py               HTTP-слой: эндпоинты
engine.py            движок: сессии, стор по организациям, журнал трейсов
registry.py          реестр генераторов
graph.json           типы с кодами (0.1 … 3.10) — порядок в интерфейсе
generators/<тип>.py  SCHEMA + context() под конкретный документ
templates/<тип>.docx шаблон с плейсхолдерами
logs_generated/      трейсы генераций (в git не попадают)
_org_store.json      накопленные значения по организациям
_etalons/ _out/      эталоны и образцы для сверки при разработке
static/index.html    legacy-фронт
```
