## 1. Цель

Довести сервис генерации `mos_generated` от текущего состояния (**1 тип:
`akt_nachala`**) до **всех generic-типов бенчмарка (~15)**: эксперт выбирает
тип → заполняет форму → сервис генерирует валидный `.docx`, каждый из которых
**автоматически подтверждается** (а) агентом-критиком против эталона и
(б) чек-сервисом `mos_analiz_refactor` (:8081) — 0 нарушений base-слоя.

**Решения владельца 2026-07-09 (рамка этого ТЗ):**
- **Графа пока НЕТ** (ждём от заказчика). Каждый тип — независимый узел:
  никакого наследования значений между типами, никаких рёбер.
- **Плейсхолдеры каждого типа — самодостаточные**: определяем САМИ под его
  эталон, без привязки к ключам других типов.
- **Эталон каждого типа определяем САМИ строго** (§4) и строим генерацию
  ровно под него.
- **Качество > экономия**: доки читать ЦЕЛИКОМ (все параграфы + все таблицы),
  когда надо посмотреть документ — смотреть (vision/PDF-рендер), не скупиться
  на чтение источников.

## 4. Выбор эталона типа + источники шаблонов

### 4.1. Эталон определяем САМИ, строго (решение владельца)
Перед шаблоном для типа выполняется **выбор эталона**:
1. Собрать ВСЕХ кандидатов типа: корпус `~/projects/_corpus/<тип>/`, папка
   бенчмарка, архив `~/Downloads/archive26-06-18/` (Mac), прод-логи
   `~/projects/mos_analiz/logs_result/<тип>/*/original/`.
2. **Прочитать каждого кандидата ЦЕЛИКОМ** — все параграфы И все таблицы
   (docx: `d.paragraphs` + `d.tables`; PDF: parsed_docs чек-сервиса или
   vision/рендер страниц). Не по кускам, не по grep — весь документ. Когда
   нужно увидеть вёрстку — смотреть глазами (vision), не скупиться.
3. Выбрать ОДИН эталон по критериям: полнота по base-правилам чек-сервиса
   типа (`doc_configs/<тип>/rules_multi.json`) · чистая вёрстка · формат docx
   предпочтительнее PDF · «верный»/OK-статус в бенчмарке предпочтительнее.
4. **Зафиксировать выбор письменно** (в отчёте типа + скил mosgen-dev §6):
   какой файл, почему он, кто были кандидаты и почему отклонены.
Эталон = единственный источник истины для шаблона и для сверки §6.2.

### 4.2. Источники docx-шаблона (по убыванию приоритета)

Критично: OK-эталоны бенчмарка почти всех типов — **PDF-сканы** (docx только у
akt_nachala и prikaz_otvetstvennyh). Для docxtpl нужен исходный `.docx`.
Порядок выбора источника:

1. **docx-болванка «_наименование предприятия_»** — чистые МР-шаблоны, лежат в
   корпусах `~/projects/_corpus/<тип>/` и папках бенчмарка (пример:
   `0.2._Приказ об отв. _наименование предприятия_ V2.docx`). Идеальный
   источник: плейсхолдерные места уже видны.
2. **docx-«верный»** из бенчмарка/архива (akt_nachala, prikaz_otvetstvennyh
   «на бланке верный»).
3. **docx реального предприятия из корпуса** (в т.ч. BAD) → вручную вычистить
   дефекты по правилам чек-сервиса (`doc_configs/<тип>/rules_multi.json` — там
   перечислено, что обязано быть) и обезличить в `{{key}}`.
4. **PDF-эталон → пересборка docx вручную** — последний вариант (дорого);
   PDF-эталон при этом всё равно использовать как визуальную сверку §3.B.

Обязательно: перед фиксацией шаблона сверить его комплектность с
**base-правилами чек-сервиса этого типа** (город=Москва, преамбула «С целью»,
номер/дата, подписант с должностью и ФИО, лист ознакомления, приложения — по
типу). Шаблон, который чек-сервис флагует, — брак источника.

## 5. Архитектура (инварианты — скил §1, здесь только дельта)

- Контракт генератора/схемы/графа/API — **строго по скилу §1.1-1.5**. Никаких
  спецслучаев «если doc_type == X».
- **Плейсхолдеры — самодостаточные на тип** (решение владельца): каждый тип
  определяет СВОЙ набор ключей под СВОЙ эталон, без обязательной привязки к
  ключам других типов. Все поля `source: "own"`. Наследования между типами
  НЕТ (механизм inherited в движке не трогаем — просто не используем, включим
  когда появится граф заказчика). Совпадающие имена для одинаковых сущностей
  (org_full, act_date…) — допустимая гигиена, но НЕ требование.
- `graph.json`: только `nodes` (doc_type/title/position — плоский список, UI
  показывает все типы), `edges` — ПУСТОЙ до графа заказчика. Гейтинг узлов
  фактически отключён (все доступны сразу).
- Сессии in-memory — ОК для MVP; персистентность НЕ добавлять без запроса
  владельца (YAGNI).
- LLM в ядре генерации ЗАПРЕЩЁН (скил §4.5): подстановка детерминированная.

## 6. 🔎 Петля самопроверки (НОВОЕ требование, решение владельца 2026-07-09)

Каждый сгенерированный документ проверяется **тремя уровнями**, все три
обязательны для DoD типа:

### 6.1. Автопроверки (скил §3.A — как было)
Паритет schema↔шаблон (`get_undeclared_template_variables`), нет сырых
`{{`/`{%` в выходе, required-валидация, валидность graph.json.

### 6.2. Агент-критик генерации (НОВОЕ)
После прогона типа спавнится **отдельный агент** (Agent tool, general-purpose),
который НЕ доверяет разработчику и проверяет против источников:
- читает эталон и сгенерированный docx **ЦЕЛИКОМ** (docx через python-docx:
  ВСЕ paragraphs И ВСЕ tables; PDF-эталон — через parsed_docs чек-сервиса или
  vision) — не выборочно, не по grep; качество важнее экономии токенов;
- сверяет 1:1: структура секций, таблицы (число колонок/строк-шаблонов),
  фиксированный методический текст НЕ искажён, значения встали в свои места,
  вёрстка/шрифт не поехали, нет дублей/пропусков в `{% for %}`;
- проверяет краевые случаи: пустые необязательные поля, длинные значения;
- вердикт «годно/не годно + конкретные расхождения». «Не годно» → правка
  шаблона/схемы → перепрогон → повторная критика (цикл до зелёного).
Промпт критику: пути к эталону и результату на стенде, доступ tool `dev`
(каждая команда с обходом sandbox), формат вердикта — по образцу
ревьюеров кампании доводки (см. `ДОВОДКА_ПРАВИЛ_состояние.md` §4).

### 6.3. Замыкание на чек-сервис (НОВОЕ — было «опц.», теперь обязательно)
Сгенерированный docx прогоняется через проверку `mos_analiz_refactor`:
```
cd ~/projects/mos_analiz_refactor && .venv/bin/python main.py \
  --doc-type <тип> --target <сгенерированный.docx> --session-dir /tmp/gencheck_<тип>
```
Критерий: **base-слой 0 нарушений** (`multi_rule_response_parsed.json`: все
`verdict.status == "ok"`). Тестовые значения формы подбирать валидными по
base-правилам типа (г. Москва, полная дата, ФИО с инициалами и т.д.).
- Для 12 доведённых типов это жёсткий гейт.
- Для НЕ доведённых (polozhenie_po, prikaz_formirovanie_po, polozhenie_comp_ppu,
  otchet_rezultatov) — информативный прогон: нарушения записать в отчёт типа;
  если нарушение указывает на брак ШАБЛОНА — править шаблон; если на брак
  ПРАВИЛА — зафиксировать, не подгонять шаблон под кривое правило.
- meth-слой — информативно (не гейт): сатурация meth известна (§3.18 скила
  mosanaliz-tune-playbook).

## 7. Definition of Done

**Тип готов** (= скил §2 DoD + новое):
1. schema = меткам шаблона (автопроверка A1);
2. `.docx` генерится через API без сырых меток;
3. агент-критик (§6.2) — вердикт «годно»;
4. чек-сервис (§6.3) — base 0 нарушений (для доведённых типов);
5. выбор эталона зафиксирован письменно (§4.1);
6. зарегистрирован в `registry.py` + узел в `graph.json` (без рёбер);
7. регресс: сервис стартует, `GET /api/graph` ок, прочие типы генерятся;
8. коммит: `feat(<doc_type>): генератор + шаблон` — identity
   `Maskedxxx <aangers07@gmail.com>`, БЕЗ Claude-постфикса, НЕ пушить.

**Волна готова:** все типы волны в DoD (типы независимы — межтиповых проверок
нет, наследование появится только с графом заказчика).

**Проект готов:** 15 типов в DoD (или 14 + согласованное исключение
